# Architecture Audit

**“문제 찾아서 고쳐”가 아니라 “문제 찾아서 보고서만 만들어”**가 포인트.

## HARD-GATE

- AI에게 바로 수정시키지 않는다.
- 전체 코드베이스(또는 사용자가 지정한 범위)를 읽고 구조를 점검한다.
- **수정하지 않는다.** 파일 쓰기·패치·리팩터·“顺便 정리” 금지.
- 감사 결과가 나와도 `refactoring-plan` / `surgical-refactoring`으로 **자동 진행하지 않는다.** 사용자가 다음 단계를 명시한 뒤에만.

관련: `minimal-path`(불필요한 일 금지), `codebase-design`(모듈·seam 어휘), `refactoring-plan`(다음 단계), `surgical-refactoring`(실행).

## 찾을 것 (필수)

1. 중복 로직
2. 지나치게 큰 파일/함수
3. 서로 다른 책임이 섞인 곳
4. 순환 의존성
5. 기능 간 결합도가 높은 곳
6. 임시방편으로 추가된 로직
7. 앞으로 기능 추가 시 문제가 될 구조
8. 현재 구조에서 정상적으로 유지되는 부분

각 문제에 심각도 **P0 / P1 / P2**를 부여한다.  
리팩토링을 권장하지 않아도 되는 부분도 명시한다.

## 리팩토링 후보 적격 조건 (architecture-audit)

현재 구조가 복잡해 보인다는 이유만으로  
리팩토링을 제안하지 않는다.

다음 조건 중 하나 이상을 만족할 때만  
리팩토링 후보로 분류한다.

1. 동일 로직이 3곳 이상 중복됨
2. 하나의 변경이 3개 이상의 독립적인 영역을 수정하게 됨
3. 기능 추가 시 기존 기능의 동작을 깨뜨릴 위험이 높음
4. 하나의 모듈이 서로 다른 책임을 3개 이상 담당함
5. 테스트/검증이 구조적 이유로 어려움
6. 현재 구조 때문에 실제 개발 속도가 저하되고 있음

단순히 파일이 크거나 코드가 길다는 이유만으로  
리팩토링하지 않는다. (감사 보고서에서도 “큼 = 후보”로 올리지 않는다. 관찰로만 적을 수 있다.)

적격이 아닌 관찰은 **관찰(비후보)** 섹션에 두고, 후보 목록과 섞지 않는다.

## 심각도

| 등급 | 의미 |
|------|------|
| **P0** | 지금 구조가 버그·데이터 손상·합의 위반·검증 불능을 유발하거나, 다음 필수 작업이 막힘 |
| **P1** | 적격 조건을 충족하고, 가까운 기능 추가/수정 비용을 뚜렷하게 키움 |
| **P2** | 적격이거나 관찰이나, 당장 손대지 않아도 유지 가능 — 보고서에는 남기되 계획 기본 제외 |

## 절차

1. 범위 확인 — 전체 vs 서브시스템. 불명확하면 한 번만 묻는다.
2. 읽기 — 진입점·모듈 경계·의존·핫스팟(최근 변경) 중심으로 조사. 코드 수정 금지.
3. 분류 — 각 항목에: 증거(파일·심볼), 적격 조건 번호(해당 시), P0/P1/P2, 후보 vs 비후보.
4. 유지해도 되는 부분 — 정상 유지 구간을 명시 (과도한 리팩터 충동 차단).
5. 보고서만 제출 — 아래 템플릿. 다음 단계 제안은 한 줄(“원하면 refactoring-plan”) 수준.

## 보고서 템플릿

```markdown
# Architecture Audit — [범위] — [날짜]

## 요약
- 후보 P0: N / P1: N / P2: N
- 비후보 관찰: N
- 코드 변경: 없음

## 정상 유지 (건드리지 말 것)
- …

## 리팩토링 후보 (적격 조건 충족)
### [P0|P1|P2] 제목
- 증거: `path` / 심볼
- 적격 조건: #…
- 왜 문제인가: …
- 왜 지금이 아닌가(해당 시): …

## 관찰 (비후보 — 큼/복잡함만 해당 등)
- …

## 권장하지 않는 리팩터
- … (이유: 적격 미충족 / 동작 안정 / YAGNI)
```

## 금지

- 감사 중 코드·테스트·설정 수정
- “고치면 이런 느낌” 구현 스케치로 파일을 바꾸는 행위
- 적격 조건 없이 P0/P1 후보 등재
- 파일 크기만으로 후보 등재
